# 会議エージェントの実装設計

Aさんが普通の会話で「会場費は3万円まで」と話す。Bさんが「AIに話す」を押して「その条件で候補を比較する時間を5分取って」と頼む。AIが2人の発言を結びつけ、2人の進行メモに「3万円以内の会場を比較・5分」という案が出る。すでに進め方が確定していれば、参加者が変更を承認するまで予定は動かない。

2026年11月10日改訂。`9e56009` 時点で会員用ワーカーが文字にするのは「AIに話す」を押した人の、その回の音声だけ。Geminiには今回の発話を渡し、お題は空欄である。Webには準備中の進行案の編集と開始後のメモ追記があり、メモはパートを配列の位置で参照している。以下は、この状態からの実装計画である。[会員用ワーカー](../apps/agent/src/classroom_agent/infrastructure/meeting_voice.py)・[Geminiへの入力](../apps/agent/src/classroom_agent/infrastructure/google_voice.py)・[Webの進行メモ](../apps/web/src/server/application/meeting-agenda.ts)

## 誰が何を持つか

| 担当                             | 持つデータと判断                                                                                                                                                                    |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pythonワーカー（1部屋に1ジョブ） | 同意して入室した人のマイクをLiveKitで受け、話者・発話区間・確定した文を部屋のメモリに保持する。今回の依頼と直前の会話を組み立て、Geminiの返答を読み上げるか、許可したツールを呼ぶ。 |
| Gemini                           | ワーカーから受け取ったお題、会話、進行状態を使い、返答またはツール名と引数を返す。                                                                                                  |
| WebサーバーとFirestore           | お題、進行案とその版、今のパート、終了予定時刻、共有メモの正本を持つ。ワーカーからの提案と参加者の操作を検証して反映する。調査を追加する段階では、調査の状態と出典も持つ。          |

ワーカーは起動・再接続時に、LiveKitのジョブが担当する部屋の状態をWebの内部APIから読む。「AIに話す」の合図を受けたら、発話を聞く間に次の読み取りを始める。先読みが終わっていれば、生成直前にWebの変更番号で更新を確認する。自動提案でも生成前に最新の進行案・メモ・サーバー時刻を取得する。

Webはワーカー用サービスアカウントのGoogle IDトークンの署名・宛先・発行元・アカウントを検証し、参加者の操作ではFirebaseのIDトークンとその部屋の参加状態を確認する。ワーカー認証の単位はサービスアカウントで、トークン自体は部屋別の権限を証明しない。[進行状態の確定とワーカー認証](technical-selection.md)

文脈の組み立てとツールの実行手順はPythonの `application` に置き、LiveKit・Google・Web内部APIへの接続は `infrastructure` に置く。Webは進行ルールを `server/domain`、検証と更新の手順を `server/application`、Firestoreトランザクションを `server/infrastructure` に置く。これで同じ会話と同じ時刻を入力にして、音声なしでも判断を検証できる。[アーキテクチャ](architecture.md)

## 実装する順番

### PR0　パートのIDを固定する

画面・API・メモの参照先を、部屋内で一意の `partId` にそろえる。Webが新規パートにIDを一度だけ発行する。改名や準備中の並べ替えでは、そのIDを引き継ぐ。

旧版ではメモを書けるのはパート開始後で、その時点から進め方は編集できない。そこで、Webは**最初の並べ替えより前に**旧配列の0番に `legacy-0`、1番に `legacy-1` とIDを付け、部屋のトランザクションで保存する。旧メモの `part: 1` は以後ずっと `legacy-1` を指す。移行済みIDを保持し、新しいパートには旧IDを再利用しない。既存パートの編集・メモ追記にIDを添えられない旧画面には再読み込みを案内する。

**合格条件**　準備中のパートは、挿入・並べ替え・移行の再実行を経ても同じIDを持つ。開始済みの部屋では、旧番号1のメモを元の「候補決め」で読める。そのパートの削除を要求しても拒否され、名前もメモも残る。

### PR1　全員の会話を聞き、前の発言を使って答える

1. 同意して入室した各参加者のマイクで発話を検出する（VAD）。文字起こし（STT）に送るのは、語頭・語尾の短い余白を含む発話区間だけ。初版は現行の同期認識を使い、余白込みで1リクエストが1分または10 MBに達する前に長い発話を分割し、確定文を発話順につなぐ。ストリーミングに移行する場合は1接続最長5分なので、途中で接続を張り直し、境目の重複と欠落を検証する。[現行の認識方式](../apps/agent/src/classroom_agent/infrastructure/google_voice.py)・[Google STTの制限](https://docs.cloud.google.com/speech-to-text/docs/quotas)
2. 「AIに話す」の合図とマイク音声は別々に届く。ワーカーの時計で合図と発話区間を記録し、合図の到着をまたぐ本人の発話は、短く遡って語頭から依頼に含める。音声が後から届く場合も、本人の同じ依頼に結び付ける。通常会話で既に認識した区間は発話IDで参照し、STTへ二度送らない。ほかの人の発話は背景の会話として拾い続ける。AI自身のトラックは購読対象から外す。
3. 部屋内の話者IDと発話時刻で確定文を並べ、実際に返したAIの返答も履歴に加える。Geminiへ渡すのは、今回の依頼、直近の会話、お題、合計時間、進行案と版、今のパートと残り時間、共有メモ。依頼の発話は一度だけ含める。初版では直近の時間とモデルの入力長に収め、履歴の要約は必要性を実測してから扱う。
4. 退室・再接続時は古いマイクの購読を解除する。音声バッファと逐語録は部屋のワーカーメモリで扱い、終了時に破棄する。ワーカーを再起動すると直前の発言履歴は失われ、Webの進行状態と共有メモから再開する。ログやエラー応答には音声・文字起こし・メモ本文・認証情報を出さない。

**合格条件**　別々のLiveKit参加者から2人分の録音を流す。Aが普通に話した会場費の条件をBが尋ねると、実際のSTT・Gemini・TTSを通じて「3万円」と返り、両端末に声と字幕が届く。合図と音声の到着を前後させてもBの依頼の冒頭が入り、同じ発話の二重送信と別室への混入がない。長い無音だけの区間はSTTに届かず、長い発話の分割境界では語句が欠けたり重複したりしない。

#### PR1の検証記録（2026年11月10日）

2つのChromiumを別の利用者としてローカルLiveKitに接続した。Aの合成音声だけに「会場費は3万円まで」を入れた。Bの質問をボタンの後、次は押下の240 ms前に再生し、両端末で同じ「3万円」の字幕と返答音、質問の語頭「さっき」を確認した。GoogleのSTT・Gemini 3.8 Flash（LOW）・TTSは実サービス。音声試験の部屋情報は固定入力で、金額を含めていない。内部APIのGoogle IDトークンを既存のローカル認証で発行する試験は権限不足。実Firestoreでは旧形式の部屋から現在パートと共有メモを読み、読み取りで移行が起きないことを別途確認した。

最終版で、Bの録音の最後の有声音から別ブラウザがAI音声を検出するまで、部屋で初めての質問は5.47秒、同じ接続での2回目は4.68秒（各1試行）。PR2の受付音声の暫定目標を初回8秒・接続済み7秒、差分か失敗通知の暫定期限を初回15秒・接続済み12秒とする。後者には今回未計測のWeb往復と検証の余裕を含めた。これらは設計目標で、p95の達成判定には実認証を含む反復試験が必要。

69.42秒の合成音声で分割位置を確かめた。原稿は同じ日本語文を繰り返した315文字。連続音では低音量フレームにノイズを足して無音検出を避け、もう一方は55秒地点に120 msの無音を入れた。両方とも分割後の連結PCMは入力とバイト単位で一致した。

| 音声         | 分割時刻 | 連結した認識結果の脱落／挿入／置換 |
| ------------ | -------- | ---------------------------------- |
| 連続音       | 53.66秒  | 0／0／0文字                        |
| 短い無音あり | 55.12秒  | 2／0／0文字                        |

この録音を再検証する際の暫定基準はフレームの欠落・重複0、文字の編集距離は315文字中2以下。実際の会話での認識率、別々の物理端末の回り込み・同時発話は未測定。

PR2の予備比較には「P1を10分から5分に短縮し、P2を10分から15分にする。P3は2分のまま」の依頼を使った。各モデルで受付種別を3回、変更後の対象・分数・合計を3回照合。いずれも3/3正解、時間切れ0。受付／分数生成の中央値は3.5 Flash-Lite（思考指定なし）が0.74秒／0.78秒、3.8 Flash（LOW）が1.39秒／1.95秒だった。PR2の初期候補はFlash-Liteとし、実際のツール操作列とWebの検証まで通して再評価する。

### PR1.5　画面の再取得と進行案の版を分け、確定後に手で編集できるようにする

現在はメモを1件書くだけで、進行案の編集判定と画面の再取得に使う `version` が進む。以下の2つを進行メモのAPIで返す。既存部屋では、分離直前の `version` を `planVersion` の初期値にし、初回の更新と同じトランザクションで固定する。[現在の版とメモ](../apps/web/src/server/application/meeting-agenda.ts)

| 変更                                     | 画面の変更番号 `version` | 進行案の版 `planVersion` |
| ---------------------------------------- | ------------------------ | ------------------------ |
| メモ追記、承認待ちの提案の表示・取り下げ | 1進む                    | 維持                     |
| 進行案の編集・確定、時刻を変える進行操作 | 1進む                    | 1進む                    |
| 同じ操作の再送で変更がなかった場合       | 維持                     | 維持                     |

画面の `since` は引き続き `version` を使う。参加者の編集フォームと書き込みには、編集を始めた時点の `planVersion` を使う。これでメモが届いても入力中の案は消えない。予定と両方の版番号は、Webが同じトランザクションで更新する。旧画面が `version` だけで予定を保存しようとしたら再読み込みを案内する。

確定後はまず参加者が手で予定を変更できるようにする。Webのdomainで、操作前の進行案と**サーバーの現在時刻**を使って次の条件を検証する。PR2の提案と承認もこの判定を共用する。[現在の時刻計算と編集条件](../apps/web/src/server/domain/meeting-agenda.ts)

- 終了済みパートの内容・順序・時刻は固定する。現在パートはID・位置・開始時刻を固定し、時間を変える場合は変更後の終了時刻が現在時刻より後であることを求める。今すぐ終える操作は「次へ進む」。
- 追加・削除できるのは現在パートより後の討議パート。末尾の「振り返り」2分と部屋の合計時間を守る。将来のパート同士で時間を振り替えても、現在パートの残り時間は変わらない。

**合格条件**　AIを起動せず2人で試す。1人がこれからのパートへ5分を振り替える間にもう1人がメモを書いても、両方が残る。同じ版から2人が予定を編集すると一方だけが反映される。10:24時点で現在パートが10:30までなら、過去のパートから5分を引く操作は拒否され、残りは6分のまま。現在パートの終了を10:24以前にする操作も拒否される。

### PR2　進行案を提案し、Webで反映を決める

Geminiに公開するツールは `propose_agenda(operations, reason)` の一つ。操作は「指定パートの後に追加」「分数を変更」「削除」「名前を変更」とする。たとえば、これからの「候補決め」が10分あるなら、次の2操作で5分を振り替えられる。

| Geminiが返す操作                         | 参加者に見せる差分                 |
| ---------------------------------------- | ---------------------------------- |
| P2の後に追加（名前・ねらい・分数を指定） | 「3万円以内の会場を比較」を5分追加 |
| P3を5分に変更                            | 「候補決め」を10分から5分に短縮    |

ワーカーは**生成開始時の進行案**にだけ通じる短い別名（P1、P2など）をGeminiに見せる。応答はそのときの対応表で `partId` に戻し、未定義の別名は拒否する。Webへ送るとき、ワーカーが担当する部屋ID・生成に使った版（`basePlanVersion`）・呼び出しIDを添える。追加分のIDはWebが採番する。承認画面にはパート名と変更前後を表示するので、参加者が対象の取り違えに気づける。

呼び出しIDはワーカーが依頼または自動提案のIDと、その中での呼び出し順から作る。Webは部屋と呼び出しIDで処理結果を記録する。まず再送かを調べ、同じ内容なら記録済みの結果を返し、同じIDで内容が異なれば拒否する。Geminiの任意の `FunctionCall.id` は、モデルに結果を返すときの対応付けに使える。

新しい提案では、Webが `basePlanVersion` と現在の `planVersion` を照合する。現在の案の写しに操作列を適用し、各操作の対象と**振り替え後の合計時間**をPR1.5のルールで検証する。提案の記録や進行案の更新はFirestoreの1トランザクションで行う。一つでも無効な操作があれば全体を拒否する。明示依頼には、Webの結果に対応する定型文をそのまま字幕とTTSに渡す。

| Webが受け取った時点の状態                                       | Webの処理                                              | 参加者に伝える文の例                                                     |
| --------------------------------------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------ |
| 準備中・版が一致・操作が有効                                    | 共有予定に即時反映し、差分を表示                       | 「進行案を更新しました」                                                 |
| 手動で確定済み、または準備開始から3分経過・版が一致・操作が有効 | 差分と「この変更を反映する」を表示。予定は承認時に更新 | 「変更案を出しました。画面で確認してください」                           |
| 版が古い                                                        | 失効させて最新状態を読む                               | 「進め方が変わったため、反映できませんでした」                           |
| 時間不足、または対象が変更できない                              | 理由を返す                                             | 「残り時間に5分の空きがありません」「そのパートは終了しました」          |
| 準備開始前、または会議終了後                                    | 状態に応じて拒否                                       | 「準備が始まると変更できます」「会議は終了しました」（終了後は画面のみ） |

承認時はWebに保存した提案を読み、入室中の参加者であること、開室状態、版、**承認時のサーバー時刻での**対象パートと残り時間を再検証する。適用と承認済みの記録も一度に書く。メモ追記や提案の表示だけでは承認を妨げない。時計だけが進んで対象パートが終わった場合は、版が同じでも拒否する。

**合格条件**

- 冒頭の「3万円・5分」の差分が両端末に出る。「提案 → メモ追記 → 承認」では予定とメモが両方残り、「提案 → 人が予定を編集 → 承認」では人の編集が残る。
- 生成中にパートが並べ替わっても、旧P3を新しいP3に付け替えない。`confirmedAt` が空で準備開始から3分をまたいだ有効な提案は承認待ちになる。承認時に対象パートが終了していれば変更を拒否する。
- 同じ呼び出しを再送しても提案は1件で、2人が同時に承認しても予定に入るのは1回。2操作のうち一方が無効なら、両方とも反映しない。

### PR2の次　会話から進行案とパートメモを自動で書く

準備中の会話から自動で案を直す処理もPR2のツールを使う。部屋ごとに、進行案の取得から生成・Webへの送信までを1件ずつ進める。「AIに話す」の明示依頼を先に扱い、待機中の自動提案は最新の確定発言にまとめる。生成中に準備中の発言が増えた場合は一度までまとめ直す。その間にも増えた発言は次の案で扱う。明示依頼が割り込んだ生成結果は破棄し、競合を声で知らせない。Webの応答が届けば次の生成に進める。参加者が承認を考えている間も会話と他の操作は続く。自動提案を口頭で伝えるときは、挙手して「どうぞ」を待つ。

自動案と明示依頼のどちらも、Webが受け取った時点で準備中なら共有予定に即時反映する。反映後も入力中の下書きは保持する。討議開始後に届いた案は承認を待つ。明示依頼の承認待ちを自動案で置き換えない。「見送る」を選んだ対象は予定の版ごとに累積し、同じパートに触れる自動案を抑止する。

各パートでは、会話から決定事項や次に確認する点を短くまとめ、**発言時点の** `partId` と追記IDを添えてWebへ送る。Webは参加者の手書きメモと同じ追記ルールで保存する。メモに発言者名を載せず、人の追記と競合しても両方を残し、同じ追記IDの再送は一件として扱う。参加者は終了後もノートで進め方と各パートのメモを読める。[提出範囲と保存要件](app-requirements.md)

**合格条件**　準備中の会話だけで案が画面に出る。自動提案と明示依頼が重なっても、明示依頼には最新の案に基づいて応え、AI自身の競合を読み上げない。会場費が決まった直後に次のパートへ移っても、遅れて届いたAIのメモが元のパートに一度だけ残り、人が追記した項目も読める。

### PR3　頼まれた調査を裏で進め、全員に出典を届ける

検索先はPR3の着手前に選ぶ。条件は、回答と出典を同じ部屋の複数人に表示でき、会議後の再閲覧も認められること。統計はe-Statなど発行元のAPIが候補。Google Cloudの標準規約20(k)(i)(1)では、自作アプリでGrounding with Google Searchの結果を表示できるのは質問した本人に限られるため、部屋に共有する調査には採用しない。[Google Cloudサービス固有規約](https://cloud.google.com/terms/service-terms)・[e-Stat API仕様](https://www.e-stat.go.jp/api/api-info/e-stat-manual)

1. 「この市民ホールの休日料金を調べて」と頼まれたら、Webに部屋・調査ID・期限・「調査中」を記録してから、ワーカーが非同期で調べる。同じ呼び出しの再送は同じ調査に戻す。音声の処理を続けながら、検索先には施設名・利用区分など必要な条件だけを送る。
2. 元資料が条件を裏付ければ、Webを通じて質問の要旨、短い回答、対応する資料名・発行元・URL・適用条件を同室に表示する。数値には対象期間・範囲・単位を添える。平日料金しか見つからなければ「休日料金は未確認」と出す。結果は先に画面に届け、音声は挙手して「どうぞ」を待つ。
3. Webは状態の読み出しと結果の受領時に、自分の時計で期限を判定する。期限を過ぎた「調査中」は「時間切れ」で返し、遅れて届いた結果を受け付けない。開いたままの画面は期限に達したらWebに再照会し、途中参加・再接続でもWebの状態を読む。資料不足、外部サービスの失敗、時間切れは別々に表示する。
4. 会議中に共有した回答の要旨・適用条件・出典は、終了後もその部屋のノートで読める。Webは結果を受け取るときに開室状態を確認し、終了後のノートは入室履歴のある利用者に読み取り専用で表示する。保存期間と削除方法はノートと共通にする。[調べものと出典の共有](app-requirements.md#調べものと出典の共有)

**合格条件**　別端末でも同じ休日料金と出典を開き、利用区分と金額を元資料で照合できる。平日料金しかない場合は「未確認」が出る。調査中にワーカーを止めても期限後に「調べています」が消え、遅れた成功結果で状態は戻らない。会議後、途中で退室した人もノートで回答と出典を読み返せる。未入室の利用者による直接取得は拒否される。

#### PR3の調査先と制限

初版は、千葉市民会館の大・小ホールの現行基本料金と、世界銀行の国・地域別の年央総人口に対応する。料金は指定管理者の表から、ホール・曜日・時間帯が一致する基本料金欄を読む。指定のないホール・時間帯は区分を列挙する。条例が定める上限額と実際の基本料金を区別するため、リンクは指定管理者の表を使う。保存するのは依頼の要旨と該当する数値・条件・出典で、ページ全文は保存しない。[千葉市民会館の施設利用料金表](https://www.f-cp.jp/shimin/guide/guide05/)・[文化庁の事実・データの取扱い](https://www.bunka.go.jp/seisaku/chosakuken/seidokaisetsu/chosakukensha_fumei/)

人口はWorld Development Indicatorsの総人口（SP.POP.TOTL）を国・年で取得する。年の指定がなければ最新の観測年を明記する。表示とノートに発行元・対象年・指標へのリンク・ライセンスを付ける。対象外の依頼は登録前にその場で知らせる。対応する調査で該当する値が見つからなければ、参考資料に「未確認」と表示する。[世界銀行の指標と利用条件](https://data.worldbank.org/indicator/SP.POP.TOTL)・[API仕様](https://datahelpdesk.worldbank.org/knowledgebase/articles/898581-api-basic-call-structures)

11月10日の実取得は施設料金2.03秒、人口1.23秒（各1回）。初期値は1部屋同時1件・依頼あたり外部GET 1回、外部HTTPは8秒、Webで登録してから30秒で失効する。部屋文書に調査を最大48件保存し、上限時は新規依頼を断る。入室履歴・保存期間・削除先はノートと共通。ワーカーの再起動後もWebの期限と共有結果は残る。予定終了後の新規依頼は断り、開室中の音声認識は続ける。「どうぞ」の許可は60秒間確保し、音声の再生完了で読み上げ済みになる。読み上げに失敗した場合は許可を解除し、ワーカーが停止した場合も期限後にもう一度頼める。

音声E2Eは、合成した質問を別々のChromiumが参加するLiveKitの部屋に流した。Google STT・Gemini・ワーカーIDトークン・指定管理者の料金表・TTSを通し、大ホールの休日全日料金と出典が両画面で一致し、「どうぞ」の前は無音、押した後は両方でAI音声を受信した。初回はSTTに失敗し、同じ音源での再試験で成功。会員認証とこの音声試験のDBはエミュレータ。実Firestoreでは別途、同時再送・読み上げ許可の競合・途中退室者のノートと未入室者の拒否を検証した。物理端末のマイク・スピーカーでの回り込みは未検証。

## 検証と、実測して決める値

各PRで、合成した会話テキスト・Webの状態・固定した時刻を入力に、文脈の組み立て、ツールの引数、競合時の結果を検証する。PR1では2人分の録音を実際のLiveKitとGoogleに流し、語頭や分割境界の聞き取り、合図と音声のずれ、応答開始までの時間を測る。依頼として遡る長さとGeminiに渡す会話の長さはこの結果で調整する。PR3では調査期限と1依頼内の呼び出し回数を検索先の応答時間で決め、同時実行は提供元の利用制限に合わせる。

最後に、音声を有効にした検証室で実機2台のスピーカーとマイクを使う。エコーキャンセルを有効にし、AIの声だけがマイクに回り込んだときは人の発言に数えず、同時に人が話し始めたときはその発言を拾えることを確かめる。話の間・重なり・字幕と声の順番も確認する。[マイクの設定](../apps/web/src/client/infrastructure/meeting-voice.ts)・[音声検証の手順](voice-probe.md)

Cloud Runの配布スクリプトは最小0台で、表示中の部屋画面は約5秒ごとに進行案を読み直す。ボタン押下時の先読みを使い、起動待ちがある初回と会議中に分けて、内部APIと発話終了から返答開始までを計測する。最小1台にするかは、起動待ちが実際の返答をどれだけ遅らせたかで決める。[配布設定](../scripts/deploy-web.sh)・[進行案の読み取り](../apps/web/src/client/infrastructure/use-meeting-agenda.ts)
