# 声・字幕の実測

会員用の部屋では、同意して入室した別々の利用者の間でマイクの音が双方向に届き、片方が「AIに話す」を押したときだけ、直前の会話を踏まえた返答音と字幕を双方が受け取ることを確認する。会員用の通話と、以下の運用者用のモデル計測は別々のLiveKit室を使う。

`/voice-probe` は、運用者1人が短い日本語の発話を試す画面。発話が途切れると、ノトが返答を字幕で表示し、同じ文を読み上げる。1回につき1部屋・1発話で、発話は20秒、ワーカーのジョブは90秒が上限。途中退室すると、その部屋の処理をキャンセルする。

## 会員の部屋で2人とAIが話す

1. WebにGoogleログイン・FirestoreとLiveKitの設定を用意し、`apps/web/.env.local` に `MEETING_VOICE_ENABLED=1` を設定してWebを再起動する。ワーカーのLiveKit接続先はWebとそろえ、Googleの設定は下の「起動」に従う。Web側の `MEETING_WORKER_EMAIL` に許可するサービスアカウント、`MEETING_WORKER_AUDIENCE` にGoogle IDトークンの宛先を設定する。ワーカー側には同じ宛先と `MEETING_WEB_ORIGIN` を設定する。内部APIは部屋が開いていることを確かめ、お題・進行案・直近32件のメモを返す。Cloud RunではサービスURLを宛先にする。ローカルで個人のADCを使う場合は、対象アカウントのIDトークンを発行する権限と `MEETING_WORKER_IMPERSONATE` が必要。
2. 次のコマンドで会員用ワーカーを起動する。1プロセスが1部屋を担当し、その部屋で繰り返し質問できる。

   ```sh
   GEMINI_MODEL=gemini-3.5-flash-lite GEMINI_THINKING_LEVEL=default make meeting-voice-worker
   ```

3. 主催者はログインして部屋を作り、招待リンクをもう1人に渡す。それぞれ別のGoogleアカウントで開く。入室前の「カメラを確認」では自分だけに映像が見える。物理端末2台で試すときは、両方から開けるHTTPSのWebとWSSのLiveKitを使う。`127.0.0.1` は各端末自身を指す。
4. それぞれ年齢・文字起こしへの同意を確認して入室すると、マイクをオフにした状態で通話につながる。話す人が会議画面でマイクをオンにして使用を許可する。入室時にプレビューは終了し、通話のカメラはオフで始まる。通話中にカメラボタンを押すと映像を共有できる。オフにすると相手の画面も頭文字に戻る。
5. お互いの声が聞こえたら、片方が「AIに話す」を押して質問する。話し終えたら「話し終えた」を押す。無操作でも本人の最後の声から、言い切りなら0.8秒、判定が難しければ1.5秒、文が続く語尾なら2.5秒待つ。文字起こしの待ち時間も含める。質問が重なった人は次の順番で押せる。質問と返答の字幕、AIの声は通話中の全員に届く。
6. 「通話を切る」で音声と映像の共有を終了し、部屋には残れる。「退室する」はその入室時の通話接続も切断する。字幕は表示中のブラウザのメモリに置く。同意してマイクをつないだ全員の発話区間をGoogle STTへ送る。ワーカーは直近の会話を部屋のメモリで管理し、Geminiに最大5分・8,000文字の履歴を渡す。閉室・再起動で履歴は失われる。

「AIに話す」で予定変更を頼むと、ワーカーは生成に使った予定の版と操作を内部APIへ送る。準備中はWebが検証した変更をすぐに反映し、両端末に差分を表示する。開始後は参加者が「この変更を反映する」を押すと、Webが対象パートと残り時間を再確認して反映する。会員用ワーカーの既定は `gemini-3.5-flash-lite`（思考指定なし）。`GEMINI_MODEL` と `GEMINI_THINKING_LEVEL` で上書きできる。

通常会話では、準備中の確定発言に合わせて進行案を提案し、討議中は決定事項と次の確認点を元のパートに追記する。音声には割り込まない。短時間の発言をまとめ、最後の有声音の時刻とWebの予定から対象を決める。振り返りの発言は共有メモの対象外。音声認識に加え、通常会話の提案・要約にもGeminiの利用料がかかる。

自動記入の音声E2Eには `MEETING_TEST_PROPOSAL=automatic` を指定する。`MEETING_VOICE_WAV` に「最初のパートの名前は会場選びにしよう」、`MEETING_BACKGROUND_WAV` に「会場費は3万円まで」の合成音声を用意する。2台のブラウザで準備中の即時反映と下書きの保持を確認して討議を開始し、金額を含むAIメモと手書きの項目が並ぶことを確認する。

音声E2Eでこの経路を試す際は、別々の合成録音を用意する。`MEETING_BACKGROUND_WAV` には「会場費は3万円まで」、`MEETING_VOICE_WAV` には「その条件で会場候補を比較するパートを5分追加し、アイデアを深める時間から5分振り替えて」と入れる。`MEETING_TEST_PROPOSAL=preparing`（準備中）または `confirmed`（確定後）を設定して `make e2e-voice` を実行する。ワーカーからローカルWebの内部APIに接続できるようにし、ブラウザの会員認証にはFirebaseエミュレータを使う。

WebはGoogleのIDトークンを検証し、Firestoreで部屋が開いており本人が同意・入室済みであることを確認して、部屋限定の30秒の接続用トークンを発行する。参加者が発信できるのはマイク、カメラ、操作メッセージ。AIワーカーは音声だけを購読する。退室開始時に新規発行を止め、LiveKitで対象の接続を切断してから退室を確定する。セルフホストのLiveKitには発行済みトークンの即時失効がない。30秒はWebが発行するトークンで新規接続できる時間であり、通話時間はこれより長くできる。[LiveKitのトークンの更新と失効](https://docs.livekit.io/frontends/reference/tokens-grants/#token-revocation)

退室操作ですぐにその端末の通話を閉じる。LiveKitの管理APIで切断を確認できない場合、ほかの端末の接続が残っている可能性があるため「退室処理中」を表示し、新しい通話トークンの発行を停止する。運用者が通話受付を止めるときは `MEETING_VOICE_ENABLED=0` にし、進行中の退室に必要なLiveKitの接続設定・認証情報を維持する。障害の場合は接続設定または管理APIを復旧させ、利用者が部屋で「退室を再試行」を押す。再読み込み後も処理中の入室から再試行できる。

検証環境は1ワーカーが同時に1部屋を担当する。空きワーカーがない部屋でも参加者同士は通話でき、画面にAIの未接続を表示する。複数の部屋に同時にAIを入れる運用には、同じ会員用エージェント名のワーカーを必要な部屋数だけ用意する。

本番有効化前の課題は、想定会議数と予算から部屋・利用者ごとのAI利用上限を決め、上限到達時に追加のGoogle呼び出しを止めること。会員用ワーカーでは通話中の通常の発話にも文字起こしの料金がかかる。

実接続E2Eは、会員用ワーカーとLiveKitを起動し、Web用の同じ接続設定と `MEETING_VOICE_WAV`（同意のある日本語WAVの絶対パス）を用意して `make e2e-voice` で実行する。Aの録音に「会場費は3万円まで」、Bの録音に「会場費の上限はいくらですか」を入れ、Aを `MEETING_BACKGROUND_WAV`、Bを `MEETING_VOICE_WAV` に指定すると、順序を変えて2回質問し、両方のブラウザで金額・音声・字幕を確認する。`MEETING_QUESTION_PREFIX` で期待する語頭も確認できる。Java 21を使う。認証・FirestoreはFirebaseエミュレータ、音声認識・返答・読み上げは課金対象のGoogle実サービスを使う。2つのブラウザのマイクに録音を流し、双方で復号した相手の音声・AI音声、返答字幕の一致、退室後の切断を検査する。

進行案の通し試験では、Webに `MEETING_WORKER_EMAIL` と `MEETING_WORKER_AUDIENCE` を渡し、同じ宛先のGoogle IDトークンを取得できる会員用ワーカーを起動する。`MEETING_TEST_FIRST_PART` に任意のパート名を、`MEETING_VOICE_WAV` に「進行案の最初のパート名を教えてください」と尋ねる録音を指定する。`MEETING_BACKGROUND_WAV` は外す。テストは主催者の画面からその名前を進行案に保存し、両ブラウザが返答音を受信し、両方の字幕に保存した名前が含まれることを確かめる。

カメラの実接続E2Eは、同じLiveKit設定で `make e2e-camera` を実行する。2つの独立したChromiumの仮想カメラを使い、入室前プレビュー、双方での映像フレームの再生、拒否後の再試行、オフと退室での撮影停止を確認する。このテストはAIワーカーを必要としない。

2026年11月9日、Mac上で独立したChromiumを2つ起動して検証した。別々のテスト利用者が同じ部屋に入り、通常の発話を互いに受信した。片方が「AIに話す」で質問すると、両方がGoogleの返答音を復号し、同じ返答字幕を表示した。片方が退室すると相手側の音声トラックも消え、退室した利用者へのトークン再発行は403になった。片方のブラウザを携帯向けのHTTPS・WSSに接続した場合にも同じ検査が通った。音源は下記の日本語録音で、物理端末のマイク・スピーカーとiPhone版Safariはこの自動検査の対象外。

MacとiPhoneを同じWi-Fiで試す場合、Mac自身はループバックのWeb・LiveKitを使える。iPhoneには、信頼する証明書を持つHTTPSのWeb・WSSのシグナリング先と、MacのLANアドレスに届くWebRTCのメディアポートが必要になる。ローカル認証を使うときは、携帯向けWebに `FIREBASE_AUTH_EMULATOR_SAME_ORIGIN=1` を設定し、テスト端末だけが使えるHTTPSリバースプロキシから認証SDKのログイン用エンドポイントを中継する。この設定は `demo-*` プロジェクトでAuthとFirestoreがともにループバックのときだけ有効。各端末で別のテストアカウントを作り、Macの6文字の招待コードをiPhoneに入力する。[iPhoneで検証証明書を信頼する手順](https://support.apple.com/ja-jp/102390)

## 起動

1. 同じLiveKitプロジェクトの `LIVEKIT_URL`（`wss://…`）、`LIVEKIT_API_KEY`、`LIVEKIT_API_SECRET` をWebとワーカーに設定する。Webは `apps/web/.env.local`、ワーカーは `apps/agent/.env` を使える。初回は各ディレクトリの `.env.example` をコピーする。Mac1台で試す場合は `brew install livekit` と `livekit-server --dev` でローカル起動できる。その場合はURLに `ws://127.0.0.1:7880`、APIキーと秘密鍵に公式のローカル開発用の値を使う。[LiveKitのローカル起動手順](https://docs.livekit.io/transport/self-hosting/local/)
2. Webの `VOICE_PROBE_TOKEN` に32文字以上のランダムな検証キーを設定する。`openssl rand -hex 32` で生成できる。画面に入力するのはこのキー。LiveKitの秘密鍵はサーバーだけで使う。
3. ワーカーの `GOOGLE_CLOUD_PROJECT` に検証先を指定する。そのプロジェクトでSpeech-to-Text APIとVertex AI APIが有効で、課金・割当が利用できることを確認する。実行アカウントには音声認識とモデル呼び出しの権限が必要。ローカルでは `gcloud auth application-default login` と `gcloud auth application-default set-quota-project <プロジェクトID>` でADCを用意できる。[Google CloudのADC](https://cloud.google.com/docs/authentication/provide-credentials-adc)
4. リポジトリのルートで以下を実行する。

```sh
make setup
make voice-worker
```

ワーカーに `voice_worker_registered` が出たら、別のターミナルで `make dev` を起動し、[音声テストを開く](http://127.0.0.1:3000/voice-probe)。検証キー・原稿・同意を入力し、「音声テストを始める」を押す。マイクを許可し、「どうぞ」が表示されてから原稿を一度読む。原稿を空にすると自由に話せる。ワーカー1台は同時に1件を受け付ける。検証を終えたらターミナルで Ctrl+C を押す。

## 何を測っているか

| 指標                               | 測定区間・単位                                                                                                                                                                                                                                      |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ブラウザで返答が聞こえるまでの目安 | マイクの最後の有声音から、復号した返答音が初めて音量しきい値を超えるまで。同じブラウザの時計（ms）を使う。前面タブで、静かな場所とヘッドフォンを使用する。物理スピーカーの出音には端末固有の遅れも加わる。                                          |
| ワーカーでの応答時間               | VADが推定した発話終了から、LiveKitの出力に最初のPCMフレームを渡すまで（ms）。発話の区切り待ち、STT、Gemini、TTSの時間も表示する。                                                                                                                   |
| 日本語の文字誤り率（CER）          | 原稿に対する置換・削除・挿入の合計 ÷ 原稿の文字数。両経路ともNFKC正規化と小文字化の後、区切り文字・句読点・制御文字など（Unicode分類 Z・P・C）を除く。「＋」などの記号（S）は採点する。0%が完全一致。数字と漢数字、漢字とかなの違いは誤りに数える。 |
| Googleの推定USD／会話1分           | その試行のSTT・Gemini・TTSの推定費用 × 60 ÷ 計測秒数。分母はワーカーの待受準備完了から返答音声の送出完了まで。STTへ送った音声秒数と各モデルの入出力トークン数を併記する。使用量が欠ければ金額は未算出。                                             |

使う言葉と録音条件で結果は変わる。「次回の集合場所を決めましょう」「来週の勉強会では、最初の15分で何を決めますか」「ノト、さっきの二案の違いは何ですか」などを複数の人・回線で試す。「測定値を保存（JSON）」で、返答モデル名とその回の数値を保存できる。成功した回の応答時間の中央値・最大値と、無応答や字幕だけだった回数を一緒に記録する。複数試行のCERは誤り文字数の合計を原稿文字数の合計で割り、1分あたりの費用は合計USDを合計秒数で割って60を掛ける。原稿は採点用にブラウザのメモリで使う。STTやGeminiには渡さない。

認識にはLiveKitのSilero VADとCloud Speech-to-Text v2の `chirp_3`（`ja-JP`、`us`）を使用する。今回は区切った一発話だけを1回のRecognizeに送る。連続ストリーミングや参加者全員を常時認識する場合は、課金対象の秒数と認識待ちが変わるので再測定が必要。[Chirp 3のリージョン・日本語対応](https://docs.cloud.google.com/speech-to-text/docs/models/chirp-3)

返答の既定はVertexの `gemini-3.8-flash`、音声は `gemini-3.8-flash-tts`（どちらも `global`）。TTSの入力文字数から日本語のトークン数を推測すると費用がずれるため、Google Gen AI SDKの各応答のusage metadataを使う。TTSの音声は生成された部分から順にLiveKitに流す。字幕を先に送るので、TTSで障害が起きても返答を読める。[VertexのTTSモデル](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/gemini/3-8-flash-tts)

単価は2026年11月8日のUSD建て。STT v2標準の最初の利用量帯が $0.016／音声1分（1リクエストを秒単位で切り上げ）。返答は100万トークンあたり、3.8 Flash が入力 $0.75／キャッシュ済み入力 $0.075／思考を含む出力 $3.75、3.5 Flash-Lite はそれぞれ $0.30／$0.03／$2.50。TTSは入力 $0.50、音声出力 $9。GeminiとTTSの導入価格は2026年12月31日までで、TTSにはクレジット還元の条件がある。実際の請求は契約、地域、割引で変わる。3つの検証コマンドの単価と計算式は [voice_cost.py](../apps/agent/src/classroom_agent/domain/voice_cost.py) を参照する。[Speech-to-Text料金](https://cloud.google.com/speech-to-text/pricing)・[Vertexモデル料金](https://cloud.google.com/model-garden/pricing)

部屋全体の原価を出すときは、同じ検証期間のLiveKitの接続時間・転送量と、Compute Engineの待機時間を含む稼働費、Webの費用を別に集め、Googleの推論費に加算する。今回はローカルワーカー1台による1人分の試行。複数人の会議は、人数・発話の割合・同時利用部屋数を記録して別途測る。

## 同じLiveKit経路で返答モデルを比べる

各試行ではワーカーを1台だけ起動する。次のいずれかで起動し、条件を替える前に Ctrl+C で終了する。

```sh
GEMINI_MODEL=gemini-3.8-flash GEMINI_THINKING_LEVEL=low make voice-worker
GEMINI_MODEL=gemini-3.5-flash-lite GEMINI_THINKING_LEVEL=default make voice-worker
GEMINI_MODEL=gemini-3.5-flash-lite GEMINI_THINKING_LEVEL=low make voice-worker
```

1行目は3.8 Flashの既定、2行目は11月8日にFlash-Liteが速かった条件（思考の指定なし。Geminiの処理は0.6〜1.2秒）、3行目は両モデルを同じ `LOW` にそろえた条件。思考レベルは `default`・`low`・`medium`・`high` から選び、既定は `low`。`default` はワーカーから思考の設定を送らず、モデルに任せる。

同じ録音・端末・接続先で試す。どの条件でもVAD（無音1.8秒）、STT、プロンプト、履歴なし、返答の出力上限（1024トークン。思考で返答が切れないよう、ローカルの検証と同じ値）、TTSのモデル・声・話速指示をそろえる。結果画面と保存JSONの `reply_model`・`reply_thinking` で、その試行を処理したワーカーの条件を確認する。Geminiの出力トークンには思考が含まれ、そのうちの思考の数を `gemini_thought_tokens` に分けて残す。返答が遅かったとき、考えた量が原因かどうかをこれで確かめる。SDKは各試行でクライアントを作る。複数回ずつ交互に測り、失敗件数、最初の音までの時間、誤り率、費用を比べる。[両モデルが対応する思考レベル](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/thinking)

`voice-check` と `live-check` はLiveKitを経由せず、ストリーミングで文字起こしする。こちらの会議1分あたりの費用は、参加人数とAIの発話回数を仮定した見込み。`/voice-probe` の費用は1人の試行の測定時間あたりであり、両者の1分換算額をそのまま比較すると分母が異なる。

## 同じ人の録音での比較（2026年11月9日）

`/voice-probe` の「比較用の録音」で20秒以内・8 MB以下の音声を選び、読み上げ原稿を入力する。ブラウザはワーカーが待受状態になったら録音をマイクと同じLiveKitトラックに一度流す。試行後も録音の選択を保つので、ワーカーのモデル・思考設定を切り替えて同じ録音を再送できる。ファイルを選ばなければマイクを使う。原稿はブラウザ内の採点にだけ使う。

Google FLEURSの日本語話者の録音（`ja_jp`、validation、行0、ID 1519、11.10秒）を使い、Flash-Lite → Flashの順に交互に各3回測定した。元の録音の `raw_transcription` は正規化後46文字。Mac上のChromiumとローカルLiveKitを経由し、STT・Gemini・TTSはGoogleの実サービスに接続した。毎回ワーカーを起動し直した。[Google FLEURS（CC BY 4.0）](https://huggingface.co/datasets/google/fleurs/viewer/ja_jp/validation?row=0)

両条件とも3回とも返答音と字幕が届いた。STTは共通なので、この誤り率の差から返答モデルの聞き取り能力は判断できない。1分換算は待ち時間も分母に入るため、Flashは1回の費用が高くても、長く待った試行があると1分あたりは低くなる。会員用の通話では同じGoogleクライアントを部屋内で再利用する。別回線・物理端末でのマイク、自由会話、2人通話の総原価はこの表の対象外。

## 検証状況（2026年11月8日）

ローカルのLiveKitとChromiumで、日本語の合成音声をマイク入力に流し、実際のGoogle音声認識・Gemini・TTSを通して字幕と返答音を受信した。Gemini 3.8 Flashが受け付ける思考レベルのうち `LOW` を使った。

成功した1試行では、発話終了からブラウザで返答音を検出するまで8.507秒、ワーカーの音声送出開始まで8.088秒。原稿は正規化後22文字で、文字誤りは0件。返された使用量から算出したGoogle推論費は会話1分換算でUS$0.01174だった。人が実際のマイクで話したときの精度や、複数試行での応答時間のばらつきは未計測。

自由発話で考え中の間に聞き取りが終わるという報告を受け、発話終了とみなす無音を0.55秒から1.8秒に変更した。原稿欄を空にし、同じ日本語の合成音声に1.2秒の無音を挟んで比較した。変更前は前半の「来週」だけが字幕に入り、変更後は後半の「図書館」も入って返答音が届いた。設定上の終了待ちは1.25秒長くなる。実際の話し言葉の誤字率はこの比較では評価していない。

## 失敗したとき

- 検証キーが通らない場合はWebの `.env.local`、ワーカーが入室しない場合は両者のLiveKit接続先とワーカーの起動を確認する。環境変数を変更したプロセスは再起動する。
- Googleの設定エラーは、ADCのプロジェクト・権限・対象API・モデル割当を確認する。画面には失敗した段階を示す。音声・文字起こし・秘密値を含みうる生の例外は返さない。
- 各試行に新しい部屋と90秒の入室トークンを発行する。検証キーを未設定にすると発行APIは404を返す。アプリは音声・字幕を保存せず、LiveKit Agentsの録音・文字起こし収集・ログ転送・トレースを無効にする。

## 調査を依頼する

会員の音声通話で「AIに話す」を押し、「千葉市民会館の大ホールを休日に全日使うときの基本料金を調べて」または「2023年の日本の総人口を調べて」と頼む。参加者全員が「参考資料」で要旨・条件・元資料を開ける。挙手中に「どうぞ（調査結果）」を押すと、AIが要点を読み上げる。音声に参加していない入室者にもWebの再取得で結果が届く。

一般のWeb資料を調べる場合は、ワーカーの `apps/agent/.env` に `TAVILY_API_KEY` を設定してワーカーを再起動する。公開の話題に続けて「これ調べて」と頼むと、対象が明確な場合だけ、短い検索質問をTavilyに送る。検索結果の抜粋から質問に答えられるとき、参考資料に日本語の要旨・根拠の一節・元ページへのリンクを保存する。従来の市民会館と人口の専用資料はこのキーがなくても利用できる。

実音声E2Eでは上のホールの質問を収録したWAVを `MEETING_VOICE_WAV` に指定し、`MEETING_TEST_RESEARCH=1 make e2e-voice` を実行する。2つのブラウザで同一のリンクと料金を読み、発行元の現行表と照合し、「どうぞ」の前後でAI音声の有無を検査する。ローカルPythonで公開サイトのTLS検証に失敗する場合は、利用環境の信頼済みCAバンドルを `SSL_CERT_FILE` に指定してワーカーを起動する。

同じ実音声E2Eで全画面マップも検証するには、下記のマップサービスをテストと同じFirestoreエミュレータに接続し、テストに `MEETING_TEST_MAP_ORIGIN`（ローカルのマップサービスのオリジン）を指定する。テスト専用の部屋で、相手のカメラを小窓に表示したまま、実際の発言がマップに載り、参考資料を開いて「どうぞ」で読み上げられることを確認する。途中で退室した利用者が閉室後に同じ回答と出典をノートから読めることも確認する。

## 通常の招待リンクで議論マップを共有する

主催者・参加者ともに「入室する」で通話につながる。最初はマイクもカメラもオフ。主催者より先に参加してもよい。会議画面のマイクをオンにすると同じ部屋の人に声が届く。字幕やマップを見たいときだけ「議論マップを開く」を押す。複数の部屋で同時に使える。カードを選ぶとその部屋の根拠の発言を読める。

マップは1セッション4人・30分まで。音声・文字ともに発言の総数に上限はない。マップへの反映待ちは最大12件で、空きができると同じ部屋で送信を再開できる。判定は発言順に直列で進み、参加者同士の音声と字幕は並行して届く。マップのパネルを閉じても通話と文字起こしは続く。主催者が「マップの共有を終了」で消去するとマップ側の文字起こしは止まるが、参加者同士の通話は続く。退室すると音声配信を止め、全員が切断して1分経つか、主催者が共有を終了すると、サーバーのメモリ上の字幕とマップを消去する。LiveKit通話も有効な部屋では、マップには本人の通話マイクのトラックを渡す。マップと会員用AIワーカーがともに稼働すると、同じ発話をそれぞれGoogle STTへ送るため、認識の利用料も各経路で発生する。マップの共有を終了しても会員用AIワーカーは動き続ける。確定した発言を共有する一本化は後続で扱う。

WebとマップのCloud Runサービスは同じWebイメージで動く。マップ側の起動コマンドは `node apps/web/scripts/run-member-map.mjs`。必要な環境変数は `GOOGLE_CLOUD_PROJECT`、`MEETING_VOICE_ENABLED=1`、`MEETING_MAP_ORIGIN`（マップ側のHTTPSオリジン）。Webの公開後、マップサービスには検証したイメージの同じダイジェストを手動で指定する。

Firestore の `roomMapSettings/default` に `enabled: true`、`origin`（マップ側のオリジン）、`session`（設定世代を表すUUID）を一度登録すると、既存・新規のすべての部屋で利用できる。段階的に配布する間だけ `roomId` で1部屋に絞れる。全体の停止は `enabled: false`。WebはGoogle認証と入室状態を確認して30秒・1回限りの接続券を返す。マップサービスは部屋ごとに接続・音声・判定待ち・マップを管理し、退室・共有終了・設定の無効化を監視する。音声・字幕・マップはFirestoreに保存しない。
